# Bookstore API — автентифікація і захист

## Варіант

- **Номер варіанта:** 1
- **Схема автентифікації:** Token
- **Право доступу:** P1
- **Throttling:** 5 запитів/год для анонімних користувачів, 100 запитів/добу для авторизованих
- **Інтеграція:** I1 — вкладений автор
- **Відеозахист:** не потрібен згідно з оновленими умовами завдання.

## Реалізовані можливості

1. Додано Token-автентифікацію через `rest_framework.authtoken`.
2. Реалізовано вхід через `POST /api/v1/auth/token/`.
3. Реалізовано вихід через `POST /api/v1/auth/token/logout/`. Після виходу токен видаляється.
4. Створено власний клас `EduDomainPermission`.
5. Читати книги можуть усі користувачі, а змінювати дані — лише авторизовані користувачі з поштою в домені `.edu.ua`.
6. Налаштовано обмеження кількості запитів: 5 на годину для анонімних користувачів і 100 на добу для авторизованих.
7. Додано вкладеного автора до відповіді книги. Для створення книги використовується `author_id`.
8. Для зменшення кількості SQL-запитів використано `select_related()`.

## Журнал `curl -i`

Для прикладів нижче використовується локальний сервер `http://127.0.0.1:8000`.

### 1. Вхід і вихід

Вхід користувача:

```bash
curl.exe -i -X POST http://127.0.0.1:8000/api/v1/auth/token/ -H "Content-Type: application/json" -d "{\"username\":\"alice\",\"password\":\"pass12345\"}"
```

Очікувана відповідь: `200 OK`, у JSON повертається токен.

```json
{
  "token": "ОТРИМАНИЙ_ТОКЕН"
}
```

Для наступних запитів використовується заголовок:

```text
Authorization: Token ОТРИМАНИЙ_ТОКЕН
```

Вихід:

```bash
curl.exe -i -X POST http://127.0.0.1:8000/api/v1/auth/token/logout/ -H "Authorization: Token ОТРИМАНИЙ_ТОКЕН"
```

Очікувана відповідь: `204 No Content`. Після видалення токена його повторне використання повинно повертати `401 Unauthorized`.

### 2. Право доступу P1

Перегляд книг без авторизації:

```bash
curl.exe -i http://127.0.0.1:8000/api/v1/books/
```

Очікувана відповідь: `200 OK`.

Створення книги авторизованим користувачем `alice`, який має пошту `alice@kpi.edu.ua`:

```bash
curl.exe -i -X POST http://127.0.0.1:8000/api/v1/books/ -H "Authorization: Token ОТРИМАНИЙ_ТОКЕН" -H "Content-Type: application/json" -d "{\"title\":\"Тестова книга\",\"author_id\":1,\"price\":\"150.00\"}"
```

Очікувана відповідь: `201 Created`.

Користувач `carol` з поштою `carol@gmail.com` не має права створювати книги. Для нього очікувана відповідь — `403 Forbidden`.

### 3. Throttling

Для анонімного користувача встановлено ліміт 5 запитів на годину.

Перевірка:

```bash
curl.exe -i http://127.0.0.1:8000/api/v1/authors/
```

Після п'яти дозволених запитів наступний запит у межах ліміту повинен повернути:

```text
HTTP/1.1 429 Too Many Requests
```

Для авторизованого користувача встановлено ліміт 100 запитів на добу.

### 4. Інтеграційна вимога I1

Під час отримання списку книг автор повертається вкладеним об'єктом:

```json
{
  "id": 1,
  "title": "Назва книги",
  "author": {
    "id": 1,
    "name": "Ім'я автора"
  },
  "price": "150.00",
  "owner": "alice"
}
```

Для створення або редагування книги використовується поле `author_id`.

Поле `author_id` не повертається у відповіді. Якщо вказати неіснуючого автора, API повертає `400 Bad Request`.

Для зменшення кількості SQL-запитів у `BookViewSet` використано `select_related("author", "owner")`.

## Дослідницькі питання

### 1. Де фізично зберігаються токени і що станеться, якщо видалити рядок вручну?

Токени зберігаються в базі даних у таблиці `authtoken_token`. Кожен токен пов'язаний із певним користувачем. Якщо видалити запис токена з бази даних, він перестане працювати. При наступному запиті з цим токеном сервер поверне `401 Unauthorized`.

Джерело: [DRF — TokenAuthentication](https://www.django-rest-framework.org/api-guide/authentication/#tokenauthentication).

### 2. Які throttle_classes має ObtainAuthToken і що це означає?

У стандартного класу `ObtainAuthToken` обмеження запитів не налаштовані: його `throttle_classes` за замовчуванням порожній список. Це означає, що стандартні глобальні обмеження DRF автоматично не захищають маршрут входу від великої кількості спроб.

Для додаткового захисту можна створити власний клас входу та підключити до нього `ScopedRateThrottle`, а також задати окремий ліміт для входу.

Джерела: [DRF — TokenAuthentication](https://www.django-rest-framework.org/api-guide/authentication/#by-exposing-an-api-endpoint) та [DRF — Throttling](https://www.django-rest-framework.org/api-guide/throttling/).

### 3. Чому для TokenAuthentication не потрібен CSRF-захист?

Токен передається в заголовку `Authorization` у кожному запиті. Браузер не додає цей заголовок автоматично до запитів на інший сайт. На відміну від cookie-автентифікації, токен не надсилається браузером автоматично, тому стандартний CSRF-захист для цього способу автентифікації не потрібен.

Джерело: [DRF — Authentication](https://www.django-rest-framework.org/api-guide/authentication/).

### 4. У якому порядку DRF перевіряє автентифікацію, права і ліміти?

У DRF спочатку виконується автентифікація, потім перевірка прав доступу, а після цього — перевірка обмежень кількості запитів.

Цей порядок можна побачити в методі `APIView.initial()`.

Якщо користувач не пройшов перевірку прав, запит не доходить до перевірки throttling. Тому запит, який отримав `401` через відсутність авторизації на закритому маршруті, не витрачає ліміт анонімного користувача.

Джерело: [DRF — APIView](https://github.com/encode/django-rest-framework/blob/master/rest_framework/views.py).
